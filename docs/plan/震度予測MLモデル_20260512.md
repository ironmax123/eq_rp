# 地震速報からの都道府県別震度予測 実装計画（機械学習アプローチ）

## 1. 概要と目的

緊急地震速報（EEW）の「震源（緯度・経度・深さ）」と「マグニチュード」を入力として、
各都道府県の予測震度を機械学習モデルで算出し、Flutterアプリ上で色分け表示を行うための
バックエンド（FastAPI）実装計画書です。
本計画は [`震度予測計算式_20260512.md`](./震度予測計算式_20260512.md)（フェーズ1）の**フェーズ3**に相当する精度向上版です。

## 2. データ取得方針

### 2-1. 主要データソース一覧

| 優先度 | データソース | 内容 | URL | 取得方法 | 注意点 |
|--------|------------|------|-----|---------|--------|
| ★★★ | **気象庁 震度データベース検索** | 震源情報 + 各観測点・都道府県別震度 (1996年〜現在) | https://www.data.jma.go.jp/svd/eqev/data/bulletin/shindo.html | Webフォームから CSV手動ダウンロード or Selenium/Playwright で自動化 | robots.txt 遵守・過負荷禁止 |
| ★★☆ | **防災科研 K-NET / KiK-net** | 強震観測点ごとの最大加速度・最大速度（PGA/PGV）波形データ | https://www.kyoshin.bosai.go.jp/ | ユーザ登録後、バッチダウンロード or `HinetPy` ライブラリ | 要ユーザ登録・利用規約確認 |
| ★★☆ | **地震調査研究推進本部（J-SHIS）** | 表層地盤増幅率 ARV / AVS30 メッシュデータ | https://www.j-shis.bosai.go.jp/ | REST APIまたはダウンロード | 商用利用時は確認 |
| ★☆☆ | **気象庁 地震月報（カタログ編）** | 長期の一括震源カタログ（1923年〜） | https://www.data.jma.go.jp/svd/eqev/data/bulletin/ | ZIP/DAT形式 → Python変換スクリプト利用 | DAT形式のパース処理が必要 |

> **推奨**: 気象庁震度データベースを一次ソースとして、都道府県別の震度情報を含む数千〜数万件のデータを収集します。

### 2-2. 目標データ量と品質

- **目標サンプル数**: 最低 5,000件（理想: 10,000件以上）
  - 目安として気象庁震度データベースには1996年以降で数万件以上の地震が収録されています。
  - 震度1以上を観測した地震を対象にすることで、教師データの質を担保します。
- **地理的バランス**: 日本海溝型（東北）、南海トラフ型（東海〜四国）、首都直下型（関東）などを満遍なく含むこと。
- **除外対象**: 震度情報のない深発地震・火山性地震など。

### 2-3. 教師データのスキーマ

```csv
# 入力特徴量 (X)
eq_lat,eq_lon,depth_km,magnitude,
target_pref_lat,target_pref_lon,
hypo_dist_km,surface_dist_km,
fault_type_int  # 0=地殻内 / 1=プレート間 / 2=プレート内

# 出力ラベル (y) ← 都道府県ごとにレコードを分割
intensity_class  # 震度0〜7 (整数8クラス分類 or 連続値回帰)
```

> **注意**: 1つの地震イベントから47都道府県分の行を生成するため、
> 地震イベント数 × 47 行のデータセットになります（N_eq × 47 rows）。

## 3. 機械学習手法の選定

### 3-1. 採用アルゴリズム比較

| 手法 | 精度見込み | M4 Pro 学習速度 | 推論速度 | NPU/GPU活用 | 推奨度 |
|------|-----------|----------------|---------|-------------|--------|
| **Random Forest** | △〜○ | ★★★ 速い（CPU並列） | ★★ 速い | CPU | △ |
| **XGBoost / LightGBM** | ○〜◎ | ★★★ 最速（CPUコア活用） | ★★★ 最速 | CPU | **◎ 第1候補** |
| **MLP（ニューラルネット）** | ○〜◎ | ★★ 中程度（MPS/GPU） | ★★ 速い | GPU (MPS) | **◎ 第2候補** |
| **k-NN** | △ | N/A（学習なし） | ★ 遅い（大規模時） | なし | × |
| **SVR** | △ | ★ 遅い（大規模不向き） | ★ | なし | × |

### 3-2. 推奨構成（2段階アーキテクチャ）

```
フェーズ3-A: XGBoost / LightGBM（表形式データ精度最優先）
フェーズ3-B: MLP（PyTorch + MPS 追加精度向上が必要なら）
```

#### なぜ XGBoost / LightGBM が第1候補か
- 表形式（Tabular）データにおいてはアンサンブル木系モデルがニューラルネットを超えることが多い（Kaggle等での実績）。
- M4 Proは多くのパフォーマンスコアを搭載しており、CPUマルチスレッドで並列化されるBoostingが最も恩恵を受けやすい。
- `scikit-learn` や `lightgbm` はApple Silicon向けにネイティブビルドされており、追加設定なしで高速動作する。
- 学習済みモデルを `.pkl` や `.json` で保存し、FastAPIから `joblib.load()` で即時ロード可能。

### 3-3. 特徴量エンジニアリング

計算式バージョン（フェーズ1）の知見を活かし、以下の特徴量を追加します。

| 特徴量名 | 計算方法 | 意図 |
|----------|---------|------|
| `hypo_dist_km` | 震源〜都道府県庁の3次元距離 | 距離減衰の近似を物理的に与える |
| `surface_dist_km` | 震央〜都道府県庁の表面距離（Haversine） | 陸上伝播距離 |
| `log_hypo_dist` | `log10(hypo_dist_km)` | 距離減衰の非線形性をモデルに示す |
| `depth_effect` | `depth_km / hypo_dist_km` | 深さの影響を距離で正規化 |
| `theoretical_pgv` | 計算式版のPGVb600の計算値 | 物理モデルの予測値を特徴量として与える |

> **利点**: 計算式バージョン（フェーズ1）の予測値をそのまま特徴量として利用することで、
> 「物理的に整合が取れている方向」を学習モデルが初期情報として受け取ることができます（モデルスタッキング的な効果）。

## 4. M4 Pro NPU/GPU 活用について（重要）

> **⚠️ 重要な注意事項**: M4 ProのNPU（Neural Engine）は**推論専用**であり、PyTorchでのモデル訓練には直接利用できません。  
> 出典: Apple Silicon ML Benchmarks（arxiv.org, 2024）、HuggingFace M4 Pro Notes

### 4-1. 学習フェーズ（Training）

| ツール | 実際に使われるハードウェア | 利用方法 |
|--------|-------------------------|---------|
| **LightGBM / XGBoost** | **CPU（Pコア 12コア）** | `nthread=-1`（全コア自動使用）|
| **PyTorch MLP** | **GPU（MPS backend）** | `device = torch.device("mps")` |
| Apple MLX | GPU + Apple Silicon 統合 | `import mlx` （将来的な選択肢）|

### 4-2. 推論フェーズ（Inference） ← FastAPIで動く部分

| 手法 | 推論速度 | NPU活用 |
|------|---------|--------|
| LightGBM `.pkl` → `joblib.load()` | < 1ms / 地震イベント | CPUのみ |
| PyTorch MPS → Core ML変換 | < 0.5ms | **ANE（Neural Engine）利用可能** |
| Core ML `.mlpackage` | < 0.1ms | **ANE最大活用** |

> **推奨**: 学習はPyTorch（MPS）で行い、`coremltools`でCore ML形式に変換することで、
> 推論時にApple Neural Engineを最大限活用できます。ただしFastAPIはPython環境のため、
> Core ML推論にはPython用`coremltools`ライブラリが必要です。

## 5. 計算時間の予測

### 5-1. データ収集・前処理

| 作業 | 推定時間 |
|------|---------|
| 気象庁震度DBからのCSVダウンロード（手動）| 2〜4時間 |
| Pythonスクリプトによるデータ整形・クリーニング | 2〜5時間 |
| 47都道府県展開・特徴量エンジニアリング | 1〜3時間 |
| **合計（データ準備）** | **約5〜12時間**（初回のみ） |

### 5-2. モデル学習時間（M4 Pro 実測ベースの推定）

> 前提: 学習サンプル数 = 10,000件（地震） × 47都道府県 = **約470,000行**、特徴量数 約15

| アルゴリズム | ハードウェア | 推定学習時間 | 備考 |
|-------------|------------|------------|------|
| **LightGBM** (n_estimators=1000) | CPU（12コア）| **約30秒〜2分** | M4 Pro CPUは高速。最速。 |
| **XGBoost** (n_estimators=1000) | CPU（12コア）| **約1〜4分** | LightGBMより若干遅い傾向 |
| **MLP** (3層, hidden=128) | GPU（MPS）| **約5〜15分** | epochs=100, batch=1024想定 |
| **MLP** (3層, hidden=128) | GPU（MPS）| **約20〜60分** | epochs=500, 過学習防止あり |

> **💡 補足**: M4 ProのCPUマルチスレッド性能（12コア）は、前世代M2 Pro比で約30〜50%の向上が見込まれています。XGBoost/LightGBMはCPU最適化が充分なため、MPS GPUを使うMLP学習より速い場合があります。

### 5-3. 推論時間（FastAPI本番時）

| 方法 | 推定推論時間（1地震イベント=47都道府県分）|
|------|----------------------------------------|
| LightGBM（CPU） | < **1ms** |
| PyTorch MLP（CPU fallback） | 約 **2〜5ms** |
| Core ML（ANE活用） | < **0.5ms** |

EEWのリアルタイム配信において、どの手法を採用しても**推論ボトルネックにはなりません**。

def load_model(path: str = "ml/models/lgbm_intensity.pkl"):
    global _model
    _model = joblib.load(path)

def predict_intensity(eq_lat, eq_lon, depth, magnitude) -> dict[str, int]:
    """47都道府県の予測震度を返す"""
    features = _build_features(eq_lat, eq_lon, depth, magnitude)  # 47行分生成
